## Behavior and exact interfaces

Added the pure client-injected `stats_aggregator/ledger.py` module, exporting the required `apply_log_counts(client, table_name: str, log_key: str, payload_digest: str, counts: dict[str, int], remaining_ms: Callable[[], int]) -> bool` and `IngestionIncomplete`. It returns true for newly completed input, false for an exactly matching completed or legacy input; unresolved interruption/service errors/content changes do not become completion.

`log_key` is bucket-qualified. Its SHA-256 is the durable identity. The supplied payload digest is independently verified against SHA-256 of UTF-8 sorted compact JSON of sanitized integer counts before writes. Counter keys sort deterministically into chunks of at most90; each chunk's transaction atomically ADDs its counters and conditionally creates `logv2#<hash>#chunk#<index>`. Chunk records retain payload/chunk digests, counter count, total chunk count and ledger version. A conditional `logv2#<hash>#complete` follows only after every chunk proof matches. Neither record has TTL or raw keys/requests/count mappings. Old marker# records remain untouched and are skipped without reading/replaying their log bodies.

Every proof read uses ConsistentRead=true. A failed/uncertain transaction, active-guard write or completion write succeeds only after an exact matching durable record is read. Otherwise it propagates. No request token is relied on; replay remains safe outside a ten-minute token window. A conflicting/malformed proof or changed aggregate digest fails closed. A false/absent response is never assumed not to have committed.

Transactions have at most91 distinct actions. Input count/type/key validation happens before writes; counts are nonnegative integers below10^38, counter keys at most1024 UTF-8 bytes. Each fixed id/count item and each record is checked against350,000 serialized bytes, each transaction request against3,500,000 bytes, and actions against100. The tiny bounded counter items and91-action ceiling keep aggregate item size below4MB as well. Existing aggregate numeric overflow is an unresolved service error, not completion. Oversized referrer hosts are dropped during sanitization so one hostile label cannot exceed the ledger key budget and stall valid document counting.

The real orchestrator now parses one complete input before calling the ledger. Valid dated records establish actual observations, including zero qualifying document requests; malformed/header-only/empty inputs do not fabricate measured zero. A zero-count empty input can still have a durable completion record. Cursor writes follow only durable v2 completion or a preserved legacy marker, and never move the cursor backwards while replaying the two-day rewind. Rewind remains anchored to saved cursor date, not current wall-clock time.

Ingestion interruption occurs before source refresh/scans/publication. The orchestrator catches only IngestionIncomplete to log a bounded category and return `{truncated: true}`, leaving the last public payload and source checkpoints untouched until a later scheduled invocation. Other failures propagate. A full ingestion pass is required before publication; this preserves consistent totals, observations and coverage and only then advances CloudFront success. The real-handler tests verify successful retry against retained partial storage rather than resetting it.

Publication scans use ConsistentRead=true and an explicit server filter for total#views, daily#, page#, referrer#, cf#daily#, source#cloudfront and source#cloudflare. Ledger/marker/cursor/guard records do not accumulate as metric rows. The accepted Cloudflare checkpoint is preserved exactly through incomplete CloudFront passes and remains handled by the D2 protocol after successful passes.

## Controller decisions and guard

The inherited plan-only text is superseded by implementation authorization. No task expands into historical reconciliation or cloud cutover.

The brief permits, but does not require, publication between completed inputs. Controller approved preserving the last public payload for any incomplete pass. Tradeoff: freshness waits for a complete pass; completed-input cursor progress is retained. This avoids mixing changed CloudFront totals with previous coverage and needs no second accepted public projection. The reader continues aging the last good payload.

Root raised a concrete missing-object risk after the first atomic implementation: a partly applied input could disappear from a future S3 listing, letting leftover counters publish. The focused real-handler RED proved it. **Ruling17** authorizes a bounded no-TTL `ingestion#active` guard storing only the expected hashed completion record (digest/numeric counts/version), strongly persisted before any chunk. Under reserved single writer it is replaced only after previous completion matches, and remains present after completion. Publication checks its matching completion independently of S3 listing. No DeleteItem permission or raw input mapping is added.

An unresolved active input is prioritized before normal ordered progress: the orchestrator streams the prefix listing, comparing hashes, resumes that input without advancing cursor during lookup, and then processes the ordinary ordered listing from the original cursor. Thus newly arrived earlier keys do not permanently block active recovery, and later completed/legacy keys cannot move the cursor past a missing active input. If its object no longer exists, publication intentionally stays blocked until evidence-backed recovery. No automatic reconstruction is attempted. The guard, chunk/completion records, accepted Cloudflare checkpoint and historical aggregates must all survive backup/migration/rollback. Cost: one extra bounded durable format/read-write responsibility and an on-recovery prefix lookup. Malformed active metadata fails closed.
